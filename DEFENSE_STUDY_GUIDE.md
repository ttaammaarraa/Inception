## 1. Preliminary Evaluation

The evaluator clones the submitted Git repository into an empty directory and confirms that it is the expected project. Only files committed to the repository count. Generated secrets and certificates must not be committed.


### Credential and cheating check

The evaluator searches tracked files for credentials, API keys, and passwords. A local `.env` file and Docker secrets are allowed, but real credentials must not be committed outside the permitted secret mechanism.

```sh
git grep -n -I -E 'password|passwd|api[_-]?key|token|secret' -- .
git ls-files | grep -Ei 'secret|credential|password|token|key' || true
git status --short --ignored
```

In this project, `srcs/.env` contains non-secret configuration only. Passwords are generated by `make secrets`, stored locally under `secrets/`, and mounted by Compose under `/run/secrets/`. Explain that secret file contents must never be pasted into documentation, logs, or commands shown during defense.

Do not run destructive cleanup commands casually. The evaluator's cleanup is intentionally destructive:

```sh
docker stop $(docker ps -qa)
docker rm $(docker ps -qa)
docker rmi -f $(docker images -qa)
docker volume rm $(docker volume ls -q)
docker network rm $(docker network ls -q) 2>/dev/null
sudo rm -rf /home/taabu-fe/data/*
```

### Forbidden configuration checks

Read the Compose file and all Dockerfiles and scripts. These are immediate failure conditions:

- `network_mode: host` or `links:` in Compose.
- `--link` in the Makefile or Docker-related scripts.
- `tail -f`, `sleep infinity`, or equivalent infinite placeholder loops.
- A background service followed by a shell, such as `nginx & bash`.
- `bash` or `sh` as the final process when the entrypoint is not actually launching the service.

```sh
rg -n 'network_mode|links:|--link|tail[[:space:]]+-f|sleep[[:space:]]+infinity|[[:space:]]&' .
```

The entrypoint may wait for a dependency with a bounded retry loop. It must eventually `exec` the real foreground service. In this project, WordPress waits for MariaDB and then runs `exec "$@"`; NGINX runs `exec nginx -g 'daemon off;'`; MariaDB runs `exec mysqld --user=mysql --console`.

## 3. Activity Overview: Oral Explanations

### How Docker works

A Docker image is an immutable, layered filesystem plus metadata describing how to start a process. A container is a running instance of an image with isolated processes, filesystem mounts, networking, and resource configuration. Containers share the host kernel, so they are lighter and start faster than virtual machines.

Docker Compose is a declarative tool that creates and connects several containers as one application. It reads the service definitions, networks, volumes, secrets, dependencies, ports, and restart policies from `docker-compose.yml`.

### Image with Compose versus without Compose

Without Compose, each container must be built and run manually with separate `docker build`, `docker run`, network, volume, environment, and dependency commands. With Compose, the same relationships are declared once and can be recreated consistently with `docker compose up`.

Compose does not change what an image is. It automates the creation of containers from images and applies the application's shared configuration.

### Docker compared with virtual machines

A VM emulates or virtualizes hardware and runs a complete guest operating system and kernel. Docker containers share the host kernel and isolate processes at the operating-system level. Containers generally use less memory and start faster; VMs generally provide a stronger isolation boundary and can run a different kernel.

### Why the directory structure matters

`srcs/docker-compose.yml` owns orchestration. Each directory under `srcs/requirements/` owns one custom image, its configuration, and its entrypoint. This prevents service-specific setup from being mixed together and makes it possible to rebuild or inspect one service independently.

### Docker network explanation

The user-defined `inception` bridge network gives containers private DNS-based connectivity by service name. WordPress connects to MariaDB at `mariadb:3306`, and NGINX connects to PHP-FPM at `wordpress:9000`. Only NGINX publishes a host port.

```sh
docker network ls
docker network inspect inception
docker compose -f srcs/docker-compose.yml ps
```

## 6. NGINX and TLS

Inspect the configuration:

```sh
grep -nE 'listen|ssl_protocols|ssl_certificate|ssl_certificate_key' srcs/requirements/nginx/conf/nginx.conf
sed -n '1,160p' srcs/requirements/nginx/tools/entrypoint.sh
```

Expected configuration:

- NGINX listens on `443 ssl` and `[::]:443 ssl`.
- TLS protocols are limited to TLS 1.2 and TLS 1.3.
- The certificate and key are mounted under `/etc/nginx/certs/`.
- The certificate can be self-signed for local evaluation.
- No host port 80 is published and no NGINX server listens on port 80.

```sh
curl -k -I https://taabu-fe.42.fr/
curl -I --max-time 5 http://taabu-fe.42.fr/ || true
openssl s_client -connect taabu-fe.42.fr:443 -servername taabu-fe.42.fr -tls1_2 </dev/null
openssl s_client -connect taabu-fe.42.fr:443 -servername taabu-fe.42.fr -tls1_3 </dev/null
```

The HTTPS request should return the WordPress site. The HTTP request must fail or have no service listening. The TLS output should show a successful handshake for the supported protocol. A self-signed certificate warning is acceptable.

Verify the certificate files and container port mapping:

```sh
ls -l srcs/certs/
docker port nginx
```

## 9. Persistence

Create a visible WordPress change and a database marker, restart the stack, and verify both remain:

```sh
make restart
docker compose -f srcs/docker-compose.yml ps
```

For a database marker:

```sh
docker exec mariadb sh -c 'mariadb -uwpuser -p"$(cat /run/secrets/mysql_password)" wordpress -e "CREATE TABLE IF NOT EXISTS persistence_check (id INT PRIMARY KEY);"'

docker exec mariadb sh -c 'mariadb -uwpuser -p"$(cat /run/secrets/mysql_password)" wordpress -e "SHOW TABLES LIKE '\''persistence_check'\'';"'
```

For the official reboot test, reboot the VM, run `make up`, reload the website, and verify that the WordPress installation, edited page, user, and database data still exist. The named volumes and host-backed data directories are what preserve the state.
